1. Core concepts

Global vs local explanation

Global: describes broad model behaviour across a population. Local: explains a particular prediction. Neither automatically proves that the model is correct or fair.

Feature attribution

Estimates how input features contribute to a model output under a defined method and background/reference data. Attribution is not proof of causality.

SHAP and LIME

SHAP uses Shapley-value-based attribution frameworks; LIME fits an interpretable local approximation around a prediction. Both require method-specific assumptions and validation.

Counterfactual explanation

Describes a change in input conditions associated with a different model output. Check whether the change is feasible, lawful, stable and meaningful for the affected person.

3. Independent validation test plan

  1. Purpose and scope: identify model owner, intended use, affected users, decision impact and prohibited uses.
  2. Reproducibility: retain model/version, input snapshot, explanation method, configuration and reference/background dataset where appropriate.
  3. Fidelity: test whether the explanation reflects the model's behaviour using method-appropriate diagnostics.
  4. Stability: test whether small, immaterial input changes produce disproportionate explanation changes.
  5. Robustness: compare explanation behaviour across relevant cohorts, time periods and reasonable alternative settings.
  6. Fairness and data quality: assess proxy effects, missingness, data representativeness and relevant group-level outcomes.
  7. Human factors: test whether intended users understand the explanation and whether it creates automation bias or false confidence.
  8. Operational monitoring: define thresholds, escalation, periodic review, change triggers and incident response.
Acceptance rule: do not declare an explanation “validated” solely because a plot or feature ranking exists. Define method-specific test criteria, record limitations, obtain independent review and link results to the model's approved use.

4. Audit-ready evidence checklist

  • Approved use case, model owner and accountable decision-maker.
  • Model card or equivalent description, version history and material limitations.
  • Input data provenance, quality controls and reference data rationale.
  • Explanation method, parameters, implementation version and reproducibility instructions.
  • Validation protocol, sample design, test results, exceptions and remediation evidence.
  • Fairness, stability, drift and human-factors testing where relevant to the use case.
  • Analyst review, override reason, escalation and final decision record.
  • Monitoring metrics, thresholds, incident log and periodic review date.
  • Source mapping showing the applicable legal, regulatory and internal-policy basis.

Illustrative transaction-monitoring scenario

A synthetic alert shows an elevated score due to transaction velocity and amount deviation. The reviewer should verify input provenance, assess the explanation's fidelity, compare with customer context and document a reasoned disposition. The explanation is not proof of suspicious activity, and a score alone must not determine a real-world outcome.

5. Boundaries and responsible use

  • Explanations can be incomplete, unstable, misleading or method-dependent.
  • Feature attribution describes model behaviour under defined assumptions; it does not establish causation.
  • Do not enter confidential customer, account, transaction or institution data into a public demonstration.
  • Use human review and institution-approved procedures for consequential decisions.
  • Do not represent this educational module as legal advice, regulatory approval or independent model validation.
