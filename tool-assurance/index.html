Tool Assurance & Evidence Register

This register explains the intended purpose, publicly described data boundaries and evidence requirements of RegTech Nexus AI review-support tools. It is a transparency register—not an audit opinion, security certification, legal opinion or claim that every function has been independently tested.

How to interpret this register

Evidence boundary: entries summarise public descriptions and identify validation needs. They do not mean that a live functional test, penetration test, privacy assessment or independent assurance engagement has been completed. Where evidence is not recorded, the status is “not verified by this register.”
Methodology

What the tool intends to assess

Purpose, inputs, rules or method, expected outputs and intended users should be described clearly enough for a reviewer to challenge the result.

Functionality

What must be tested

Representative workflows, boundary conditions, calculation examples, error handling, exports and browser behaviour require repeatable test evidence.

Data & security

What must be substantiated

Processing, storage, network requests, browser storage, third-party services, retention and access statements should match observed implementation and documented controls.

Public tool profiles

These are initial profiles. They intentionally separate public product descriptions from claims that still require validation.

Flagship · Financial crime

TradeGuard

Trade-finance and transaction-risk review support using rule-based indicators.

Publicly stated boundary
The product page says the tool supports review, does not determine money laundering or legal liability, and requires an authorised human reviewer. It advises against entering confidential documents in the public workspace.
Evidence to retain
Rule catalogue and version, test cases and expected results, indicator rationale, data-flow observations, report/export tests and release history.
Verification status
Public description reviewed for this register. Live functionality and technical security controls have not been independently verified here.

Flagship · Policy & controls

Policy Gap Analyzer

Policy-to-control review signals and evidence-gap action planning.

Publicly stated boundary
The product page describes browser-local analysis, recommends synthetic or non-sensitive excerpts, and states that outputs are review signals—not compliance certification or a legal/regulatory decision.
Evidence to retain
Source-pack registry, official source and applicability notes, matcher test cases, browser network/storage checks, output/export tests and known limitations.
Verification status
Public description reviewed for this register. Browser-local processing and all functions require technical re-verification before relying on that claim.

Minimum review method

Control stepMinimum evidenceReview outcome
1. Discover sourceIssuer, jurisdiction, exact instrument, official URL and publication date.Source is traceable to the primary issuer.
2. Verify applicabilityRelevant provision, scope conditions, effective date, amendments and supersession check.Applicability is supported, qualified or marked for verification.
3. Map requirementRequirement-to-control mapping, assumptions and rationale.Mapping is reviewable, not automatic legal interpretation.
4. Test functionalityTest input, expected output, actual output, pass/fail, date and version.Observed behaviour is distinguished from untested claims.
5. Check data boundariesBrowser/network inspection, storage and export behaviour, third-party requests and disclosure review.Data-handling claims match observed behaviour or are corrected.
6. Approve and monitorReviewer, review date, issue log, next review trigger and change history.Material changes can be traced and re-tested.

Regulatory source freshness

Prefer official regulator or standards-body publications. Check the current instrument, amendment history, effective date and transition provisions. A source link alone does not establish applicability or correct implementation.
